# 协作会话 / AI 草稿 — 产品设计说明（草案）

本文档与 [`HANDOVER.md`](./HANDOVER.md) 配合阅读：描述 **会话生命周期、首启与新建规则、群内匹配展示、个人主页与邀请、草稿列表交互**。实现时可按里程碑拆分。

---

## 1. 产品定性（回顾）

- **只有一种会话形态**：协作向会话；**置顶行** = 快捷入口，等价于 **新建一条 `ai_draft`**（允许多条草稿并存）。
- **阶段**：`ai_draft`（仅与 AI 整理）→ `collab_active`（已创建计划 + 群）→ 群内再做匹配与人选。
- **开启协作**：无表单必填；由服务端基于会话上下文做 **合规 + 「清晰具体」判定**；优先支持用户 **用聊天确认** 发起（详见前文评审结论），并保留降级手动入口。
- **消息**：立项即 **云端持久化**（按 `sessionId` 存消息表）。

---

## 2. 首启与「新建协作」（对应讨论 §8）

### 2.1 理想状态 vs 落地体验

- **理想**：用户第一次打开小程序时 **会话列表为空**，必须点 **「新建协作」** 才出现第一条 AI 会话。
- **落地（更好理解）**：**首次打开**时由系统 **默认创建一条 `ai_draft`**（可带一句欢迎/引导），让用户立刻理解「这是一条可以说话的协作会话」。
- **本质**：用户若要 **再开一条新会话**，仍应通过 **「新建协作」**（或等价入口），而不是依赖首启那条无限复用。

### 2.2 空草稿去重（避免刷屏）

- 若已存在 **`ai_draft` 且用户从未发送过任何内容**（仅有系统/AI 欢迎语，无用户消息），用户 **再次点击「新建协作」** 时：
  - **不新建第二条空会话**，而是 **进入该条已有空草稿**（焦点落到对话）。
- 若当前草稿（或任意草稿）里 **已有用户发送的内容**，再点「新建协作」→ **新建一条新的 `ai_draft`**。
- 文案可对运营说明：**「未开口的草稿不重复占行」**，列表更干净。

## 3. 会话列表与草稿交互（对应 §8）

### 3.1 置顶行（列表第一行）

- 固定展示：**新建协作 / 小陈助手** 等统一文案（与 UI 稿一致）。
- 点击行为：遵守 **§2.2**（有空草稿则进入，否则新建）。

### 3.2 列表行左滑（草稿 vs 协作会话区分）

- **草稿行（`ai_draft`）**：左滑露出 **「置顶」「删除」**（常见列表交互；图标与文案用自有设计，**不照搬**第三方应用）。
  - **置顶**：该草稿在列表内靠前展示。
  - **删除**：删除该草稿及关联云端会话消息（需 **二次确认**）。
- **协作会话行（`collab_active`）**：左滑 **仅「置顶」**，**不提供删除**。避免误触导致退群/解散/列表与云端状态不一致；若用户需退出协作，应在 **群内或设置等明确入口** 操作（另立需求时再细化）。

### 3.3 说明

- 协作会话 **只做置顶**，与草稿的「置顶 + 删除」略有不一致，但符合「协作关系不能随便列表里一滑就没了」的预期。

## 4. 群内匹配展示与安全（对应 §6，已定稿）

### 4.1 展示内容原则

- **脱敏摘要**：仅展示为「匹配场景」准备的短摘要（对方协作意图要点），**不**默认暴露完整 AI 私密对话。
- **用户匹配意愿**：例如公开标签、意向类型、是否接受邀请等（与现有 `xc_match_profiles` 等能力对齐时再定字段）。
- **头像可点击**：进入 **对方资料页**（单独页面，见 §5）。

### 4.2 匹配人数（100 → 10）

后端可混合多种信号，**产品侧用白话理解**即可：

| 术语 | 白话 |
|------|------|
| **纯标签** | 看双方填的标签、意向类型是否对得上。 |
| **LBS** | 看地理距离，优先近的（若用户开了位置）。 |
| **向量** | 把文字意图编成数学相似度，找「说得像一类事」的人（实现成本高，可后期）。 |
| **人工运营池** | 运营配置的候选人或加权名单，用于冷启动或活动。 |

接口形状建议：服务端返回 **Top N（如 10）卡片**，每张含：`openid`（内部用）、展示用 **昵称、头像 URL、脱敏摘要、意愿标签**；**不要**在下发包里带对方完整会话原文。

## 5. 对方资料页 +「邀请 TA」（对应 §6）

### 5.1 已定稿：单独「对方资料」页面（不复用「我的」）

**白话**：点头像出来的是 **对方的公开简介**，**必须与**底部「我的」里 **自己的主页** 分开——两套页面，不要混用，避免设置、勋章、菜单与对方资料搅在一起。

**落地（已定）**：单独新增小程序页面 **「对方资料」**（展示用标题可用「Ta 的协作名片」等；开发路径建议 `pages/user-preview/**`，在 `app.json` 注册）。  
群内匹配、会话列表等凡「看别人」，一律 **跳转该页**，**不得**用 `profile` 加参数凑合。「我的」仍只服务当前登录用户本人。

### 5.2 展示范围（合理且克制）

- **路由**：由群内匹配点头像 → `navigateTo` 打开上述 **对方资料页**（带上对方用户标识，由开发在技术方案里定参数名）。
- **页面上展示**：
  - 头像、昵称（或脱敏昵称策略若需要）
  - **公开标签 / 协作意向摘要**（脱敏版）
  - **信用展示惯例**（若业务已有：履约率等可公开字段）
  - **不展示**：完整聊天记录、手机号、精确地址等非匹配必要隐私

### 5.3「邀请 TA」按钮位置（推荐）

1. **首选**：页面 **底部固定操作栏**（安全区内），主按钮 **「邀请 TA」** —— 单手可达、与「看完资料再行动」习惯一致。
2. **备选**：若页面极短，可将次要操作放导航栏右侧；主行动仍建议留在底部。
3. **交互**：点击后走邀请链路（通知 / 卡片 / 进群审批等产品已定流程）；失败时用 toast 说明原因。

## 6. 实现优先级建议（供排期）

1. `xc_sessions` + `xc_session_messages` + 首启种子草稿 + 空草稿去重 + 列表左滑（**草稿**：置顶+删除；**协作会话**：仅置顶）+ **`pages/user-preview` 对方资料页**。
2. `evaluate` / `promote` 云函数与聊天页按 `sessionId` 读写。
3. 群内匹配卡片（10 头像 + 摘要）+ 点头像进 **对方资料页** + 底部「邀请 TA」。
4. 匹配排序：先 **标签 + LBS + 运营池**，向量检索后置。
